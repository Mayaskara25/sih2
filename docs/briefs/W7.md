## TASKS

### 1. `app/main.py` — Streamlit front end
- Upload **1 or 2 images**. Accept GeoTIFF/TIFF plus PNG/JPEG.
- **An explicit per-image modality selector** (`optical` / `msi` / `sar` / `unknown`), pre-filled with what `satquery.io.resolve_modality` auto-detected, and pass the user's choice through as `forced_modalities`.

  > **This selector is load-bearing, not a convenience.** W0's resolver deliberately returns `unknown` rather than guessing when a bare 1- or 2-band file carries no filename hint — which is exactly what real Cartosat PAN and RISAT products look like. On the hidden ISRO evaluation set the user's explicit choice may be the only thing that makes the cross-modal path work at all. Show the auto-detected value **and which precedence tier decided it** (`RasterInput.modality_decision` carries the mechanism and reason), so the user knows when they are overriding a guess versus a filename hint.
- Free-text query box, plus a few one-click example queries (use the problem statement's five representative queries).
- Run button → `run_query(...)`.

### 2. Result view — evidence, not just text
- The answer (`trace["result"]`).
- **Confidence shown together with `confidence_basis`.** Never render a heuristic as if it were a probability. The basis is one of `stub | heuristic | calibrated | model_logprob`; label it in plain words ("heuristic estimate", "model log-probability", "placeholder — specialist not yet implemented"). Presenting a stub's `0.0` as a real confidence would be exactly the kind of drift PLAN.md §2.4 exists to prevent.
- **Visual evidence** from `trace["artifacts"]`: `mask`, `overlay`. Render them when present, and degrade gracefully when `None` (which is the norm while specialists are stubs).
- Show the input images themselves via `RasterInput.display_rgb` — **always use that**, never try to render raw bands yourself. It is guaranteed `(H, W, 3)` uint8 and already handles SAR dB scaling, NaN, and 1/2/4/12-band inputs.

### 3. Execution-summary panel — this is a graded rubric row, make it prominent
Render the trace as something a judge can read at a glance, **not a collapsed JSON blob**:
- task selected, and **why it routed that way** — `trace["routing"]` has `mechanism` (`rule` / `exemplar_nn`), `matched`, `score`, `alternatives_considered`
- models/tools used — `trace["models_used"]`, each with role, name, precision, device
- parameters, timings (`trace["timings_ms"]`), run id
- validation warnings and errors, visibly distinguished

The problem statement says internal reasoning is **not** evaluated and only the observable execution trace is. Treat this panel as a primary deliverable.

### 4. Handle failure honestly
`run_query` returns a trace with `validation.passed == False` for a refusal (e.g. two optical images sent to fusion — that is the R2 guard doing its job). **Render the refusal and its reason clearly**; do not swallow it or show a blank result. A crash re-raises after writing its trace — catch it, show what was attempted, and link the trace.

### 5. `satquery/report.py` — downloadable per-query report
PDF or self-contained HTML containing: query, inputs (with modality and how it was decided), answer, confidence + basis, visual evidence, and the **full execution trace**. Keep the dependency light — a self-contained HTML string is entirely acceptable and avoids a PDF toolchain; if you want PDF, declare it in `requirements/extra-w7.txt`.

### 6. Be honest about latency
Model load is tens of seconds on this hardware once real specialists land. Use Streamlit's spinner/status; never leave the page looking frozen. Cache what is safely cacheable — but **do not cache model objects in module globals**; models are acquired via `satquery.runtime.model_pool` and the card is 3.9 GB (§4.3).

## TASKS

### 1. `satquery/controller/router.py` — query text → task
Route to exactly one of `{vqa, caption, grounding, change, fusion}` (the `TaskName` literal in `contracts.py`).

Two tiers, per PLAN.md §3.4, and **record which one fired**:
- **Tier 1: deterministic rules** — keyword/pattern matching. Tried first.
- **Tier 2: exemplar nearest-neighbour** — if no rule fires confidently, compare the query against embedded task exemplars. Keep this dependency-light; a simple TF-IDF / token-overlap similarity over a handful of hand-written exemplars per task is entirely acceptable and avoids loading a model. **Do not** load a transformer for this, and **do not** put an LLM in the routing path — this is the one rubric row that rewards being deterministic and auditable.

Emit a `RoutingInfo` (`contracts.py`): `mechanism` (`"rule"` | `"exemplar_nn"` — these are the only two legal values, see `ROUTING_MECHANISMS`), `matched`, `score`, `alternatives_considered`.

**THE CENTRAL TRAP — this is R4 and the rubric will probe it:**
> Query text must be able to override input count. Two images + *"describe the first image"* must route to **`caption` on image 1**, NOT to `change`. Two images + *"what changed?"* routes to `change`. One image + *"what changed?"* is a validation error, not a route.

A router that just counts files passes casual testing and fails the requirement. Handle the disagreement between what the query asks for and what the inputs allow, explicitly, and make the resolution visible in the trace.

Also handle: which image a single-image task should run on when two are supplied (default to the first; let the query say "second"/"latter" if it does).

### 2. `satquery/controller/validate.py` — pre-dispatch compatibility checks
Before any specialist runs, build a `ValidationInfo` (`passed`, `warnings`, `errors`) and an `InputInfo` per image. Use `satquery.io.load_raster` / `resolve_modality` — **do not open a raster yourself** (§5.3; `raster.py` is the only reader in the repo).

Check at least:
- file exists; format supported; band count plausible for the claimed modality
- image count matches the routed task (change/fusion need exactly 2; vqa/caption/grounding need ≥1)
- for `change`: both images comparable (same size; same CRS if both georeferenced) — warn, don't hard-fail, on mild mismatch since W4 can register
- for `fusion`: **the two inputs must be genuinely distinct modalities.** Two optical inputs is a hard error (R2). This is the check that stops us claiming cross-modal analysis on two optical images.
- **A modality of `"unknown"` is a WARNING, not an error.** W0's resolver deliberately returns `unknown` rather than guessing when a bare 1- or 2-band file carries no filename hint — which is exactly what real Cartosat PAN and RISAT products look like. Surface it loudly so the app can prompt the user, but never refuse to run on it.

Distinguish warnings (proceed, record) from errors (refuse, record, still write a trace).

### 3. `satquery/controller/trace.py` — the auditable record
Write `runs/<run_id>/trace.json` matching `contracts.ExecutionTrace` (PLAN.md §4.2) on **every** run — successful, validation-failed, **and crashed mid-inference**. A crash with a trace explaining what was attempted is worth far more than a silent crash; wrap dispatch so an exception still produces a trace before propagating.

Notes that will otherwise cost you a debugging session:
- `models_used[]` entries need a **`device`** key (`"cuda"`/`"cpu"`). `satquery.runtime.model_pool.get_execution_metadata()` returns exactly the right shape — call it rather than hand-rolling.
- **Coerce every number with `float()` / `int()` before it enters a payload.** The validators reject `np.float32`/`np.int64` on purpose, because `json.dump` rejects them too. This is the single likeliest cause of a late integration failure (PLAN.md §4.5).
- Validate your own trace with `contracts.validate_execution_trace` before writing it.
- `runs/` is gitignored. Never commit a trace.

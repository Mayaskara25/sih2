# W1 — Data Acquisition

**Status: IN PROGRESS.** Branch `w1-data`. Started 2026-08-29.

## Headline: BigEarthNet is solved and is no longer the project's #1 risk

PLAN.md v2 treated BEN acquisition as a possible multi-session ordeal with an abort trigger,
because the imagery is two monolithic `.tar.zst` archives totalling **117.7 GB** with no
sharding and no HuggingFace mirror. That framing was based on documentation. Probing the
actual artifacts changed the answer.

**Measured, not inferred:**

| Fact | Value | How established |
|---|---|---|
| S2 archive | 63,251,710,377 B | `curl -I` content-length |
| S1 archive | 54,439,153,171 B | `curl -I` content-length |
| Range/resume support | **NONE** — Zenodo returns `200` + full length for a `Range` request | direct test |
| Tar layout | `<archive>/<acquisition_folder>/<patch>/<patch>_<BAND>.tif` | streamed first 8 MB, listed members |
| S2 patch on disk | ~165 KB (12 bands: 4×29 KB, 6×7.5 KB, 2×1.2 KB) | member sizes |
| S1 patch on disk | ~116 KB (VV + VH) | member sizes |
| Join key | `patch_id` (S2 name) ↔ `s1_name` | read the real parquet |
| Official splits | train 237,871 / val 122,342 / test 119,825 of 480,038 | `split` column |

**The pairing trap was real.** S1 and S2 order their archives by different acquisition
folders — the S1 partner of the *first* S2 patch lives in a different S1 folder entirely.
Naively early-stopping both archives yields **unpaired** patches, which would have silently
produced a useless training set. Paired yield had to be computed from the metadata:

| First *k* folders of each | Paired patches | Stream | Countries | Classes |
|---|---|---|---|---|
| 5 | 7,010 | ~5.1 GB | 2 | 17/19 |
| **10** | **13,630** | **~8.6 GB** | **4** | **19/19** ✅ |
| 20 | 19,646 | ~15.9 GB | — | 19/19 |

**Decision: k=10.** It is the smallest prefix containing all 19 land-cover classes — k=5
misses two, which would leave the contrastive encoder blind to them. ~3.8 GB stored.

**Disclose in the writeup (§5.9):** the slice is 4 European countries (IE, PT, FI, AT), a
prefix rather than a stratified draw, because a stratified draw costs 117.7 GB of streaming.
That is a defensible trade-off — state it, don't imply the sample is representative.

## Landed: RSVQA-LR test split ✅

Verified against the **Zenodo API** (record 6344334) before writing any fetcher, not taken
from the recon doc — total 150,463,070 B across 12 files, which matched recon this time.

Fetched (`data/rsvqa_lr/`, 99,771,189 B, all sha256-verified, `verify.py` → **PASS**):
`Images_LR.zip` (95,008,155 B) + the three test-split JSONs. Extracted: **772 images,
256×256, 3-band**, all loading through W0's `load_raster` and correctly tagged `optical`.

`--hr` is refused in code (exit 2), not merely discouraged: RSVQA-HR's test images ship
only inside a 13.5 GB archive that also carries the train images.

Honest note recorded in the manifest: `Images_LR.zip` holds images for *all* splits — there
is no test-only image archive. At 95 MB the concern behind §2.2a's rule isn't engaged, but
it is written down rather than glossed over (§5.9).

### Two bugs found by actually running it

1. **`verify.py` could not be run as a script** — it does `from scripts.data.common import …`
   with no `sys.path` bootstrap, so `python scripts/data/verify.py` died on
   `ModuleNotFoundError`. Its tests import it as a module, so they passed. Fixed.
2. **Manifest `root` must be relative to the data root** (`rsvqa_lr`, *not* `data/rsvqa_lr`).
   `verify.py` computes `data_root / manifest.root`, so a duplicated prefix made it look in
   `data/data/rsvqa_lr` and report **NOT_DOWNLOADED for data that was present**. That is a
   false negative that would trigger a pointless re-download. My fetcher's bug, not
   `verify.py`'s — but every later fetcher must follow the same convention.
3. Fetchers must **skip files already present at the expected size**. Without it a re-run
   re-downloads everything, and an interrupted re-run leaves a stale `.part` beside a
   perfectly good file (observed).

## Landed: BigEarthNet S1+S2 paired slice ✅

**13,630 paired patches, 0 dropped.** `verify.py` full sha256 → **PASS**.

| | |
|---|---|
| Files / bytes | 190,820 files, 3,824,687,040 B (3.56 GiB) |
| Splits | train 6,519 / validation 3,599 / test 3,512 |
| Countries | Ireland 5,361 · Portugal 4,947 · Finland 1,673 · Austria 1,649 |
| Class coverage | **19 / 19** |
| Annotations | `BigEarthNet.txt.parquet` 466,819,745 B, 9,553,962 rows |
| Selection | k=10 symmetric (`counts.k` in the manifest) |

Independently confirmed: 13,630 S2 `_B04.tif` and 13,630 S1 `_VV.tif` files — exact match,
which is the pairing guarantee holding. A 400-target spot check found 0 patches missing a
half. Both sides load through W0's `load_raster`; S1 tags `sar` and takes the dB path.

**It took two attempts.** The first died mid-S2-stream (`zstd: premature end` →
`tarfile.ReadError`), exactly the no-resume hazard §2.2b documents. The second completed.

### ⚠️ For W2: BigEarthNet stores ONE BAND PER GeoTIFF

`load_raster` returns `band_count=1` for a BEN patch file — each of the 12 S2 bands and 2 S1
bands is its own `.tif`. There is **no multi-band stacking helper anywhere in the repo**.
`benclip`'s 14-channel stem (§3.1) needs one, and W2 must build it — inside
`satquery/adapters/benclip.py`, per §4.5 (band logic lives there and nowhere else). Do not
put stacking in `raster.py`; that is W0-owned and frozen.

### Manifest size decision

The BEN slice manifest is **55 MB** (190,820 per-file sha256 entries) — too much for every
clone to carry forever. Resolution: the full manifest is **gitignored but kept on disk** so
`verify.py` still checks integrity byte-for-byte, and a compact summary is committed at
`docs/manifests/bigearthnet_s1s2_slice.summary.json`. **No reproducibility is lost** — the
slice is fully determined by `metadata.parquet` (whose sha256 *is* committed, via the
annotations manifest) plus the folder-rank selection in the fetcher plus k.
The summary lives under `docs/` rather than `data/manifests/` because `verify.py` globs that
directory and would report an entry-less summary as a spurious NOT_DOWNLOADED.

### Note on the asymmetric optimisation

`--folders 5 --s1-folders 10` was measured to yield the identical 13,630 patches for a
projected 4.20 GB instead of 6.76 GB. It is **committed and available for future re-fetches,
but the data on disk was produced by the symmetric k=10 path** — the run that used it was
started, then killed as redundant once the k=10 run was confirmed complete and verified.
The manifest records `k: 10`, so on-disk provenance is accurate and the committed code
reproduces it with `--folders 10`.

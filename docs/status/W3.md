## Grounding DINO fp16 is broken on this stack — found and fixed (contract pressure on §3.2)

Reproduced directly against `IDEA-Research/grounding-dino-tiny` outside this
module: loading in fp16 (W0's `modelpool.py::_load_grounding` default for
CUDA, per PLAN.md §3.2) and running a forward pass raises
`RuntimeError: expected scalar type Half but found Float` deep inside the
deformable-attention encoder's `grid_sample` call — a float32 sampling grid
mixed with half feature maps. `pixel_values` was already cast to the model
dtype before the call; the mismatch originates inside the model's own
reference-point computation, not in caller-side dtype handling.

**Fix:** `grounding.py` does not edit the frozen `modelpool.py`. Instead it
registers a corrected fp32 loader for the `"grounding"` role via
`ModelPool.register()` — the extension point `modelpool.py`'s own docstring
documents ("Add or override a role spec") — before every `run_grounding`
call (`_ensure_fp32_grounding_role`, idempotent). The registered `RoleSpec`
reports `precision="fp32"` truthfully, so `get_execution_metadata()` /
the trace never claims fp16 for a model actually running in fp32.

**This is a real divergence from PLAN.md §3.2's precision table** (fp16 for
grounding) and is flagged here per §5.5 for the orchestrator's attention.
Recommendation: fold this fp32 loader into `modelpool.py::_load_grounding`
directly once W0/orchestrator can edit that file, since the fp16 path is
provably broken on this transformers/torch combination, not just slower.

fp32 grounding-dino-tiny measured peak `torch.cuda.max_memory_allocated()`
**≈1,550 MB** for one grounding call (well inside the ~2.5 GB budget implied
by the work order, with no other heavy model resident at the time).

## Grounding — verified end-to-end on real data

Ran directly (not just via pytest) against `data/rsvqa_lr/Images_LR/232.tif`:

```
run_grounding(image, "a road")
  -> 1 box, label "a road", confidence 0.497
  -> overlay_path exists on disk (real PNG, box drawn), e.g.
     runs/artifacts/grounding/<uuid>.png
  -> confidence_basis = "heuristic"  (see rationale below)
```

Zero-detection path verified honest: raising the detection threshold so
nothing clears it (`SATQUERY_GROUND_THRESHOLD=0.999`) yields
`bounding_boxes == []`, `confidence == 0.0`, and an overlay file is still
written (a plain rendered copy of the image, no fabricated box) — this exact
scenario is one of `tests/test_w3_grounding.py`'s CUDA-gated tests and
passes.

Bugs from `old_files/models_registry.py::run_grounding` fixed, not carried
forward:
- the duplicated `score = ...` line — removed; score computed once in
  `_to_contract_box`.
- label coercion — `_coerce_label` handles `text_labels` vs `labels`, bare
  ints, empty strings, and always falls back to the query text, unit-tested
  directly (`test_coerce_label_*`, 5 cases).
- box order — `_to_contract_box` converts native `[xmin,ymin,xmax,ymax]` to
  the contract's `[ymin,xmin,ymax,xmax]`, clamps the inverted case so the
  `ymin<=ymax`/`xmin<=xmax` validator invariant always holds, and coerces
  every number (including numpy scalars) to a Python `float` — unit-tested
  including a numpy-scalar input case (PLAN.md §4.5).

**Honest domain-shift finding (not a code bug):** on the 256×256 RSVQA-LR
aerial tiles, Grounding DINO's *top-scoring* box collapses toward the
whole-image extent (e.g. `[0,0,256,256]`-ish) for most text queries
("a road.", "a building.", "water.", "a residential building." all showed
this at threshold 0.05, checked directly against raw HF outputs, ranks 2+
localize much more tightly but score lower). This looks like an out-of-domain
effect — Grounding DINO was trained on natural photographs, not aerial
tiles — not a bug in this module; reproduced with the raw HuggingFace
model/processor with no code from this repository involved. **IoU against a
referring expression is explicitly NOT measured** — VRSBench (PLAN.md's
IoU>0.3 check) is not downloaded yet, exactly as the work order anticipated;
that check moves to W8.

`confidence_basis` for grounding is `"heuristic"`, not `"model_logprob"`,
by deliberate choice: the value is Grounding DINO's own raw per-detection
sigmoid score taken directly with no rescaling — it is model-native, not a
hand-rolled rule, but `"model_logprob"` in this contract specifically means
a *mean token log-probability from text generation* (what `run_vqa`/
`run_caption` use below), a technique this module does not implement.
Claiming it here would mislabel the technique (PLAN.md §5.9). `"heuristic"`
is the closest honest fit among the four allowed enum values; this exact
reasoning is also inlined as a code comment at the point of return.

## VQA / Captioning — implemented, unit-tested, CUDA e2e pending model download

`run_vqa` / `run_caption` acquire `Qwen/Qwen2-VL-2B-Instruct` through
`model_pool.using("vqa")` (never a module global), build a chat-template
prompt via `processor.apply_chat_template`, and generate with
`do_sample=False`.

**`confidence_basis = "model_logprob"`**, computed as:
```
transition_scores = model.compute_transition_scores(sequences, scores, normalize_logits=True)
confidence = exp(mean(transition_scores over the generated tokens))
```
i.e. the geometric mean of the model's own per-token probabilities for the
answer it actually generated — a real property of the model's output
distribution, not a hand-rolled rule. Unit-tested with a hand-built fake
model exposing known softmax probabilities
(`test_confidence_from_scores_computes_geometric_mean_token_probability`):
confirmed the computed value equals `sqrt(0.5 * 0.4)` exactly for two
synthetic generation steps with probabilities 0.5 and 0.4. Falls back to
`(0.0, "heuristic")` only on genuine extraction failure (empty `scores`,
`compute_transition_scores` raising, or no finite log-probs) — never
silently mislabeled as `"model_logprob"` when it isn't. Every number is
coerced with `float()` before entering the payload.

Prompting: RSVQA-LR's answer vocabulary was inspected directly
(`LR_split_test_answers.json`, 10,004 active QA pairs across
`rural_urban` / `presence` / `count` / `comp` types — answers are `yes`/`no`,
`rural`/`urban`, or bare integers, e.g. `"403"`, `"47"`). The VQA prompt
explicitly asks for "the shortest possible correct answer... a single word,
a short phrase, or a bare number" to match that vocabulary, since
accuracy/BLEU scoring rewards brevity (per the work order).
